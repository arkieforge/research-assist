# Arkie API

The Cloudflare backend. One Worker hosts every chat's Durable Object agent, the JSON routes the web app calls, and the queue consumer that keeps the chat index in Neon. Everything it runs on is declared with Alchemy in this package.

## Owns

- Chat agents (`ChatAgent` Durable Objects): history, streaming, tools (`render_html`, T3 Code over MCP).
- The auth gate: Clerk JWT → user id, and chat ownership from the instance name.
- `GET /chats` (Neon via Hyperdrive) and `GET /artifacts/:id` (D1 + R2) for the web app.
- The ChatEvents queue consumer.
- Every stage's infrastructure, and the account-level bootstrap.

## Code map

- [`alchemy.run.ts`](./alchemy.run.ts): the app stack, one copy per stage. Thin; composes `infra/`.
- [`infra/bootstrap.run.ts`](./infra/bootstrap.run.ts): the bootstrap stack (deploy token, Doppler, GitHub, Vercel). Admins only.
- `infra/`: `api.ts` (the Worker and its bindings; `ApiEnv` is inferred here), `database.ts` (Neon or local Postgres, Hyperdrive), `resources.ts` (R2, D1, queue), `observability.ts` (Axiom, incident.io), `config.ts` (deploy-time config), `stages.ts` (stage rules), and custom resources: `local-postgres.ts`, `doppler.ts`, `vercel.ts`.
- `src/`: runtime code. `worker.ts` (routing, gate, routes, consumer), `agent/` (the agent, the Replay (dev) model), `db/` (Drizzle schemas and clients), `lib/` (auth, chat names, T3 allowlist, events), `types.ts` (response shapes web imports as `@arkie/api/types`).
- `migrations/neon`, `migrations/d1`: generated by `vp run db:generate`, applied on deploy and in dev.

## Working locally

From the repo root, `vp run dev` runs this with everything else; `vp run dev --only api` runs it alone. It's `alchemy dev` on stage `dev_<user>_<checkout>`: workerd, local D1/R2/queue/Durable Objects, Postgres in Docker, state in `.alchemy/`. No cloud account.

```sh
vp run --filter @arkie/api test        # vitest
vp run --filter @arkie/api typecheck
vp run dev:destroy                     # reset this checkout's local stage
```

Read Alchemy's and Effect's own source when the docs fall short: `vp run sync:repos` puts the exact installed versions in `/.repos` (read-only).

## Deploying

| Stage                    | How                                   | Notes                                                                    |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------ |
| `prod`                   | push to `main` (Deploy API workflow)  | owns the Neon project, Axiom, incident.io, Vercel production env         |
| `pr-<n>`                 | `preview:api` label on a PR           | Neon branch of prod's project; points that PR's Vercel preview at itself |
| `live_<user>_<checkout>` | `vp run api:deploy` from your machine | your own cloud copy; needs Doppler `stg` access                          |

All deployed stages read secrets, cloud credentials included, from Doppler (`stg` or `prd`), so a contributor needs a Doppler login and nothing else. Details: [deploy.md](../../docs/operations/deploy.md), [secrets.md](../../docs/operations/secrets.md), [bootstrap.md](../../docs/operations/bootstrap.md).

## Adding infrastructure

1. Declare it in the `infra/` module it belongs to (or a new one), and yield it from `alchemy.run.ts` or bind it in `infra/api.ts`'s `env`. Its runtime type reaches `Env` by inference.
2. Make it work in all three kinds of stage: check whether Alchemy has a local implementation for `alchemy dev` (most Cloudflare resources do; Neon doesn't, hence `local-postgres.ts`).
3. New config goes through `infra/config.ts` and into Doppler (see secrets.md). Optional values use `optional()`, so an empty CI variable reads as unset.
4. No provider? Write a small custom resource like `infra/doppler.ts` over the service's REST API, with a delete that is safe to run twice.
5. Verify with `vp run dev:destroy && vp run dev --only api` and, for cloud-only parts, a `preview:api` PR.
